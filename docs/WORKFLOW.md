# Флоу роботи над QuizRoom

Документ для двох людей, які керують ШІ-кодерами. План того, **що** будувати, — у `docs/00-common.md`, `docs/A-server.md`, `docs/B-client.md`. Тут — **як** працювати, щоб дві незалежно згенеровані половини зійшлися.

## 1. Як це влаштовано

| | Кодер A | Кодер B |
|---|---|---|
| Частина | сервер | клієнт |
| Зона | `server/**`, `README.md` | `client/**` |
| Гілка | `server` | `client` |
| Етапи | `0`, `A1`–`A5` | `B1`–`B6` |
| Стартовий промпт | `prompts/coder-A-server.md` | `prompts/coder-B-client.md` |
| Журнал | `docs/progress-A.md` | `docs/progress-B.md` |

Три речі тримають усе разом:

1. **Контракт** (`shared/src/index.ts` + `docs/00-common.md` §6) — заморожений після етапу 0.
2. **Зони** — файли двох кодерів не перетинаються, тому конфліктів у git не буває.
3. **Скіл `quiz-stage`** (`.claude/skills/quiz-stage/SKILL.md`) — однакова процедура виконання етапу для обох: контекст → передумови → реалізація → доведення кожного AC → журнал → коміт → звіт.

## 2. Одноразова підготовка

Репозиторій уже створено, а етап 0 (каркас монорепо і контракт) виконано й лежить у `main`. Лишилось:

1. Домовтесь, хто A, а хто B.
2. **Обидва:** встановити Node.js ≥ 22.12, клонувати репозиторій, виконати `npm install`.
3. **Обидва:** нова сесія ШІ в корені репозиторію → стартовий промпт → `/quiz-stage 0 verify`. Потім ручна перевірка з `docs/01-stage-0.md`: відкрити сторінку з телефона в тій самій мережі.
4. Створити й запушити гілки: A — `git switch -c server && git push -u origin server`, B — `git switch -c client && git push -u origin client`.

Це точка синхронізації **SP0**: далі працюєте паралельно.

## 3. Цикл одного етапу

Однаковий для всіх етапів і обох ролей.

1. **Оновити гілку.** `git fetch origin && git merge origin/main` у своїй гілці.
2. **Нова сесія ШІ.** Один етап — одна сесія з чистим контекстом. Вставити стартовий промпт своєї ролі.
3. **Запустити етап:** `/quiz-stage A2` (свій ID).
4. **Не заважати.** Кодер сам читає план, перевіряє передумови й працює. Якщо зупинився з питанням — відповісти по суті; якщо просить вийти за правила (нова залежність, зміна контракту) — див. §6.
5. **Прочитати звіт.** У таблиці AC кожен рядок має доказ. ✅ без доказу — попросити показати вивід команди.
6. **Ручна перевірка.** Виконати все з блоку «Ручна перевірка для людини» у звіті.
7. **Дефект?** У тій самій сесії описати симптом («на 360px кнопка вилазить за екран»), а не рішення. Кодер виправляє і повторює перевірку етапу.
8. **Переглянути diff.** Пʼять хвилин очима: чи розумієте ви цей код? Якщо ні — попросіть кодера пояснити або спростити. Вам це захищати.
9. **Злити в `main`:**

   ```bash
   git switch main && git pull
   git merge --no-ff server          # або client
   npm install && npm run typecheck && npm test
   git push origin main
   git switch server                 # назад у свою гілку
   ```

10. **Повідомити партнера** («A2 у main») і закрити сесію.

Порядок етапів: A — `0 → A1 → A2 → A3 → A4 → A5`; B — `B1 → B2 → B3 → B4 → B5 → B6`; потім разом — `I`.

## 4. Точки синхронізації

| Точка | Умова | Що стає можливим |
|---|---|---|
| SP0 | етап 0 у `main` | обидва стартують |
| SP1 | A1 у `main` | B може виконувати B4 (список і редактор квізів) |
| SP2 | A3 у `main` (краще A4 — з ботами) | B може виконувати B5 (realtime) |
| SP3 | A5 і B6 у `main` | спільний етап I |

B1–B3 не потребують сервера, тому зазвичай A встигає до SP1 і SP2 раніше, ніж вони знадобляться B.

Якщо партнер запізнюється — **не** починайте залежний етап «на заглушках». Краще виконати `/quiz-stage <його ID> verify` на `main` і допомогти знайти, що не сходиться.

Дізнатись стан робіт у будь-який момент: `/quiz-stage status`.

## 5. Правила git

- У `main` потрапляє тільки етап, у якого всі AC ✅ (ручні — перевірені людиною).
- Кожен мерджить тільки свою гілку. У чужій зоні нічого не правимо навіть «очевидне» — пишемо партнеру.
- `git push --force` у `main` не використовуємо.
- `package-lock.json` змінюється лише на етапі 0. Якщо він змінився пізніше — хтось додав залежність усупереч R3: відкотити (`git checkout origin/main -- package-lock.json && npm install`) і розібратись.
- Конфлікт під час мерджу означає, що хтось вийшов за свою зону. Не розвʼязуйте його навмання: зʼясуйте, чий файл, і залиште версію власника.

## 6. Зміна контракту

Повна процедура — `docs/00-common.md` §9. Коротко: кодер зупиняється і записує запит у свій журнал → ви вдвох погоджуєте → **A** вносить зміну окремим комітом у `main` (`shared/src/index.ts` і §6 разом) → обидва підтягують `main` і запускають `npm run typecheck`.

Більшість «потрібно змінити контракт» насправді розвʼязується у своїй зоні. Спершу попросіть кодера запропонувати варіант без зміни контракту.

## 7. Коли щось іде не так

| Симптом | Що робити |
|---|---|
| Кодер утретє виправляє той самий AC | Зупинити. Нова сесія: `/quiz-stage <ID>` — скіл підхопить незакомічену роботу. Описати проблему своїми словами |
| Кодер робить більше, ніж у «Вимогах» | Зупинити, нагадати про «Поза межами етапу», зайве прибрати (`git restore <файл>`) |
| Кодер змінив `shared/` або чужу зону | `git restore --source=origin/main -- shared/` (або чужу теку), потім `/quiz-stage <ID> verify` |
| Після мерджу `main` зламався | `/quiz-stage <ID> verify` на `main` для останніх етапів обох ролей — звіт покаже, чия зона |
| Сесія «забула» правила або обірвалась | Нова сесія зі стартовим промптом; стан відновлюється з журналу й робочого дерева |
| Телефон не відкриває сторінку | Граблі G2 і G3 у `docs/00-common.md` §8 |
| Порт 3001 або 5173 зайнятий | Залишився процес попередньої сесії: `lsof -ti :3001 :5173 \| xargs kill` (macOS / Linux) |

## 8. Етап I і репетиція

Етап I (`docs/00-common.md` §10) виконуєте разом за одним ноутбуком і з реальними телефонами: `/quiz-stage I` проведе по чеклисту. Знайдений дефект виправляє власник зони у своїй гілці звичайним циклом із §3, після чого сценарій повторюється. Завершення — сценарій демо з §11, пройдений двічі поспіль без збоїв.

## 9. Якщо ваш інструмент — не Claude Code

Промпти й план не привʼязані до інструмента. Скіл — це звичайний Markdown: якщо команда `/quiz-stage` недоступна, напишіть кодеру «виконай етап A2 за процедурою з `.claude/skills/quiz-stage/SKILL.md`». Вміст `CLAUDE.md` скопіюйте у файл правил свого інструмента (`AGENTS.md`, `.cursorrules` тощо).
